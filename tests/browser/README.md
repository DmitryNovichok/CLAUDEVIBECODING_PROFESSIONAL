# Проверки интерфейса и отчёт по аудиту

Запускать на обычном Linux/macOS/Windows с поддержкой Chromium. Тесты используют только временную SQLite, вымышленные аккаунты, синтетические задания и локальный Pyodide 0.28.3. Адрес production, чужие аккаунты и ключи не нужны. Два клиента Together соединяются с настоящим временным сервером по WebSocket. Привилегии учителя, проверка ответов и скачивание проходят через настоящие HTTP-обработчики.

## Запуск

Из корня репозитория сначала соберите обычные производственные `app.js` и `min/` по инструкции проекта: приложение в fixture получает именно эти файлы. Несобранные изменения исходников не попадут в браузерную проверку.

```sh
cd tests/browser
npm ci --ignore-scripts
npx playwright install --with-deps chromium
npm run test:list
npm test
```

`test:list` только перечисляет сценарии и **ничего не подтверждает об интерфейсе**. При запрете запуска браузера операционной системой остановитесь и перенесите выполнение на обычный CI-хост. Скрипты не отключают sandbox, не подменяют Chromium и не обходят ограничения среды.

Частичные запуски:

```sh
npm run test:ui
npm run test:python
npm run test:performance
npm run test:ui -- --grep '320px'
npm run report
```

`npm test` включает также независимые CSP-сценарии. `PYTHON` может указывать путь к штатному Python 3.11+. `fixture.cjs` ограничивает время старта и закрытия сервера; незакрывающийся fixture означает ошибку прогона, а не успех. При использовании helper вне Playwright всегда вызывайте `await fixture.stop()` в `finally`.

## Как читать результат

После **фактического запуска** `npm test` создаёт:

- `audit-summary.json`: результат каждого сценария (`passed`, `failed`, `blocked`, `skipped`, `not-run`), попытки, ошибки и ссылки на вложения. Отсутствующий отчёт или ошибка старта браузера не считаются пройденным тестом.
- `results.json`: исходный машинный отчёт Playwright.
- `playwright-report/`: HTML-отчёт; `test-results/`: вложения, снимки и трассы ошибок.
- В основных сценариях — PNG, дерево доступности и JSON размеров/описаний полей. Они появляются только при посещении страницы настоящим браузером.

Снимок экрана — материал для проверки человеком, а не автоматическое одобрение дизайна. `visualReview` намеренно остаётся `not-performed/pending`. Перед выпуском просмотрите состояния 320, 375 и desktop: обрезанный текст, перекрытые/недоступные кнопки, крупный шрифт, выделение фокуса и ошибки формы. Сравнение ширины документа не обнаружит все обрезания внутри контейнеров.

Это адресные проверки доступности. Они не доказывают полное соответствие WCAG, работу всех экранных дикторов, браузеров или устройств. Performance JSON описывает синтетический профиль и ограничения измерений; реальные значения появляются только после успешного выполнения теста. Режим `test:list` не создаёт новый итог проверки и не должен использоваться как свидетельство успешного прогона.
