# Проверка восстановления и нагрузки

Проверки не устанавливают обновление, не меняют рабочую базу и не отправляют письма. Оператор запускает их после размещения согласованной версии исходников. Результаты синтетического сценария не являются обещанием времени восстановления сервера.

## До обновления или восстановления

```sh
python3 /opt/trainer/deploy/preflight.py --app /opt/trainer --backups /opt/trainer-backups --port 8000 --verify-latest
```

Проверяются синтаксис Python, соответствие исходников и ресурсов, формат и права частных настроек, SQLite, место под полный снимок, его возраст и контрольные суммы, совпадение версии работающего процесса. Содержимое паролей и имена учеников не выводятся. Отсутствие нового полного снимка до первого запуска `backup.sh` ожидаемо: сначала создайте его, затем повторите проверку. Если окружение службы отличается от оболочки, путь `EGE_PRIVATE_CONFIG` передайте явно. Не выводите переменные с паролями в общий журнал.

Перед плановым восстановлением отдельно подтвердите наличие конфигурации Caddy/systemd, переменных службы и пароля шифрования внешних копий. Они не входят в снимок каталога приложения. Оставьте место под распаковку: оценка preflight использует запас до трёх объёмов данных.

## Реальный запуск восстановленной копии без замены сайта

```sh
python3 /opt/trainer/deploy/recovery_check.py /opt/trainer-backups/trainer-ВЫБРАННЫЙ.tar.gz --source /opt/trainer
```

Скрипт проверяет все хеши, распаковывает данные в новый временный каталог, копирует доверенные исходники и запускает отдельный процесс только на `127.0.0.1` со свободным портом. SMTP в этой копии отключается. Проверяются версия `/api/health` и сохранность количества записей работ, попыток, решений и занятий. Процесс останавливается, временная копия удаляется. Новые снимки записывают версию и отпечатки всех корневых Python-модулей (включая вынесенные обработчики и протокол проверки), истории версий и манифеста ресурсов; при несовпадении укажите в `--source` соответствующий сохранённый релиз. Старые снимки без этой записи требуют самостоятельной сверки версии. Проверка релиза перед обновлением отдельно обходит локальные импорты сервера и отклоняет архив с пропущенным модулем до замены файлов.

Независимый исполнитель Python — отдельная служба: данный сценарий не устанавливает и не запускает контейнеры. По [инструкции исполнителя](python-runner/README.md) отдельно сохраняются закреплённый ID образа из `/etc/ege-python-verifier/image`, доверенные файлы `/opt/ege-python-verifier`, пользовательская служба systemd, tmpfiles, настройки пользователя и диапазонов subuid/subgid, а также OCI-образ либо данные для воспроизводимой сборки из закреплённой основы. После восстановления сначала выполняются `python_executor.py --probe` и контейнерные приёмочные тесты от пользователя исполнителя. Отсутствие этих проверок нельзя заменять успешным `/api/health` веб-сервера; до готовности исполнителя независимая проверка должна оставаться недоступной.

Для оставляемой вручную копии используйте `snapshot.py restore` в новый пустой каталог, разместите там соответствующие исходники и укажите `--banks <каталог-копии>/banks`. Не запускайте исходники из рабочего `/opt/trainer`, рассчитывая, что одна смена текущего каталога перенаправит базу: пути вычисляются относительно самих исходников.

## Воспроизводимый синтетический сценарий

Из корня исходников:

```sh
python3 tools/recovery_drill.py --output /tmp/egeshka-recovery.json
python3 tools/load_lesson.py --students 60 --seconds 300 --interval 10 --output /tmp/egeshka-soak.json
```

Первый сценарий создаёт временный класс, работу, сохранённый ответ, код, вложение «Вместе» и внешний банк. После снимка добавляется ещё один результат. Восстановленный сервер должен вернуть прежние работу, ответ, код и файлы через настоящие HTTP-маршруты, а результат после снимка должен отсутствовать. Отчёт показывает время подготовки снимка, время до работоспособной копии и фактическую давность последнего восстановленного результата. Это локальные RTO/RPO только данного эксперимента: загрузка архива, ожидание оператора, DNS/TLS и размер рабочего банка в них не входят. Дневное расписание само по себе допускает потерю до суток данных, а при сбое копий — больше; нужный интервал выбирается по допустимой потере.

Нагрузочный сценарий использует 60 временных учеников и около 15 тысяч синтетических заданий. После начального всплеска идут чтение условий/истории и автосохранение кода с интервалом 10 секунд, с отдельным keep-alive соединением на ученика. Записываются ошибки, p50/p95, ожидание блокировки SQLite, пик памяти и сохранённые ответы. Измеренный интервал может быть короче заданного на один период опроса; незавершённый новый цикл в конце не запускается. Скрипт не принимает адрес рабочего сайта или путь к рабочей базе.

## Профиль начальной загрузки

```sh
cd tests/browser
npm ci --ignore-scripts
npx playwright install --with-deps chromium
npx playwright test performance.spec.cjs
```

Профили: окно 1366×768, CPU ×4, сеть 4 Мбит/с и задержка 100 мс; окно 390×844, CPU ×6, сеть 1,6 Мбит/с и задержка 150 мс. Это эмуляция относительно машины выполнения, а не проверка конкретного школьного компьютера или телефона. Используются синтетические учётные записи, данные и локальный сервер. Холодный кэш задаётся явно. Вложения отчёта содержат FCP/LCP, наблюдаемую готовность главной, длительные задачи, смещения макета, размеры скриптов и снимок экрана. Время фиксируется без выдуманного пройденного норматива; размеры проверяются против бюджетов. Если браузер заблокирован средой, переносите запуск в разрешённый CI/стенд, не отключая ограничения безопасности.
