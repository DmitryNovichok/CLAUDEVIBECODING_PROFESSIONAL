# Приёмка установленного релиза

`python3 deploy/acceptance.py` собирает один JSON-отчёт по оставшимся
эксплуатационным условиям аудита S06/S08/S11/R01/R04. По умолчанию команда
только читает локальную конфигурацию и БД. Она не меняет аккаунты, сессии,
настройки служб, рабочую БД и не отправляет письма.

Статусы имеют разные значения:

| Статус | Значение | Код завершения |
|---|---|---|
| `pass` | Выполнена именно указанная проверка, в указанном окружении | 0, только если весь отчёт принят |
| `fail` | Проверка обнаружила несоответствие или явно запрошенная проба не прошла | 1 |
| `pending` | Нет нужного свидетельства либо требуется проверка оператором | 2, если нет `fail` |

**Общий отчёт останется `pending`, пока не выполнены ручные эксплуатационные
условия.** Скрипт намеренно не превращает наличие SMTP-конфига в подтверждение
доставки, локальный архив — в доказательство удалённого хранения, а маленький
пример Python — в полную приёмку изоляции. У отчёта нет ключа «считать всё
готовым». JSON не следует публиковать: он описывает готовность инфраструктуры,
хотя пароли, адреса почты, токены и содержимое записей в него не попадают.

## Один отчёт

На сервере, под пользователем с правом чтения конфигурации и БД:

```sh
python3 deploy/acceptance.py \
  --app /opt/trainer \
  --archive /private/rehearsal/trainer-retrieved.tar.gz \
  --url https://YOUR_DOMAIN \
  --probe-runner \
  --runner-report /private/rehearsal/runner-report.json \
  --revision EXACT_RELEASE_COMMIT_SHA \
  --migration-db /private/rehearsal/anonymized-old.db \
  --anonymized \
  --output /private/rehearsal/acceptance-new.json
```

Пути и домен — примеры; используйте реальные значения. `--output` создаёт
новый файл с закрытыми правами и отказывается перезаписывать существующий.
Флаг `--anonymized` — подтверждение оператора, **не автоматическое
обезличивание**. Если обезличенной старой БД пока нет, не передавайте её:
проверка останется `pending`.

Каждый необязательный аргумент добавляет явное действие:

| Аргумент | Что фактически происходит |
|---|---|
| `--archive` | Полная проверка списка файлов, SHA-256, SQLite integrity, времени **из манифеста** и соответствия версии/хешей кода. Архив старше 26 часов или от другого релиза не считается текущей проверенной копией. |
| `--url` | Два GET-запроса без cookies: `/welcome` и `/api/health`, с обычной проверкой TLS. Проверяются действующие CSP, HSTS, nosniff и версия. Redirect не принимается и не обходится. `--expected-version 2.74.0` задаёт целевую версию явно; иначе сравнение идёт с локальным релизом `--app`. |
| `--probe-runner` | Фиксированная программа `print(6 * 7)` через штатный защищённый Unix-сокет. Основная БД и прогресс не участвуют. Запускайте с теми же правами, что и сайт (`trainer`); fallback на Python хоста отсутствует. |
| `--runner-report` и `--revision` | Проверяются формат, свежесть до 24 часов, неизменяемый образ, нужные четыре теста, ноль пропусков/ошибок и совпадение коммита. Это свидетельство из указанного отчёта, а не доказательство, что тесты выполнены на текущем сервере. Отдельно остаётся probe установленной службы. |
| `--migration-db --anonymized` | Законченный обезличенный снимок копируется в закрытый временный каталог. В отдельном процессе дважды выполняется инициализация БД **новым** кодом; Python запрещает создание сокетов и запуск дочерних процессов, SMTP-политика пустая. Проверяются integrity, схема, количество и значения защищённых записей, связи результатов и владельцев. Временная копия удаляется. |
| `--migration-db --private-local-copy` | Та же проверка законченного **необезличенного** снимка, остающегося на контролируемой машине. Никакой выгрузки и обезличивания не происходит. Для получения согласованного снимка работающей БД используйте команду ниже. |

Для `--migration-db` нужен законченный SQLite-снимок, без `-wal`/`-shm`/`-journal` и без
символической ссылки. Не передавайте работающую БД. Подготовьте копию через
SQLite backup API и обезличьте **копию**: контакты, имена, логины, IP,
идентификаторы/тексты обращений, коды приглашений, пароли/хеши, сессии, ссылки
восстановления, код и свободный текст учеников. Сохраните связи и разнообразие
состояний, необходимые для миграций. Проверьте обезличивание отдельно.
Копия и отчёты должны оставаться на контролируемой машине, вне Git.

Запускайте только заранее проверенный доверенный код кандидата. Запреты Python
предотвращают случайные сетевые обращения и запуск внешних команд при миграции.
Это не изоляция средствами ОС для исполнения недоверенного кода или нативных
расширений; неизвестный релиз с рабочими данными этим инструментом не проверяют.

Если первая миграция изменила число или значения существующих записей, отчёт
выдаёт `pending` с именами таблиц и агрегированными счётчиками: некоторые старые
ошибочные попытки могут удаляться намеренно. Сравните это с правилами миграции.
Отпечатки содержимого используются только внутри процесса и в отчёт не попадают.
Изменение оценок/владельцев/наград при прежнем количестве строк теперь тоже
обнаруживается. На первом проходе сравниваются существовавшие в снимке столбцы;
на втором — все столбцы после миграции. Изменение значений при втором запуске или
появление новых нарушенных связей даёт `fail`. Прежние нарушения связей требуют
разбора (`pending`), даже если новых не появилось.

Список защиты содержит 27 таблиц: результаты вариантов и самостоятельных, ответы,
сохранённый код, прогресс курсов, владельцев классов и учеников, историю монет,
подарков и корректировок опыта, работы и попытки МЦКО, варианты и ответы
«Интеллектуального мегаполиса», прогресс Arduino и просмотренных уроков.
`protected_table_names` перечисляет именно найденные в исходном снимке таблицы
из этого списка; `protected_tables` — их количество. Произвольные имена других
таблиц исходной БД в отчёт не попадают. Связи старых результатов не выводятся из текущего
класса ученика: после выполненной работы ученик мог законно перейти в другой класс.
Это проверка сохранности записанных значений, а не правильности оценки по смыслу
задания или работы всех экранов.

## Проверка рабочей базы на самом VPS

Когда обезличенной копии ещё нет, можно выполнить репетицию **на VPS**, оставив
все персональные данные там. Проверяемый релиз должен находиться в отдельном
каталоге; работающая установка `/opt/trainer` не заменяется. Запустите из
проверенного каталога кандидата (пример пути ниже) под пользователем, которому
разрешено читать установленную БД:

```sh
umask 077
mkdir -p /private/rehearsal
python3 /private/releases/egeshka-2.74.0/deploy/rehearse_upgrade.py \
  --installed-app /opt/trainer \
  --candidate /private/releases/egeshka-2.74.0 \
  --private-local-copy \
  --output /private/rehearsal/migration-2.74.0.json
```

Команда открывает исходник в SQLite `mode=ro` с `query_only`, получает
согласованную копию через SQLite backup API, в том числе при действующем WAL,
и проверяет её новым кодом в отдельном процессе. Записи сервиса могут продолжать
появляться параллельно; флаг `source_unchanged` относится к закрытому снимку,
а не к запрету рабочему приложению сохранять ответы во время проверки. SQLite
может обновлять служебные отметки чтения `-shm`; основной файл БД и WAL команда
не записывает. Временный каталог имеет права `0700`, снимок — `0600`; после
проверки снимок удаляется. При сбое нет сообщений с содержимым записей.

Отчёт содержит только версии, статусы и агрегаты проверок, без имён, почты,
ответов, кода и отпечатков частных записей. Файл отчёта создаётся с закрытыми
правами и не перезаписывает существующий. Саму БД передавать в чат или Git не
нужно. Новый результат проверяется вручную; наличие команды не считается её
выполнением на рабочем сервере. Настройки SMTP, учётные записи и служба при этой
репетиции не изменяются. Проверки почты и второго фактора выполняются отдельно.

## Что оператор должен подтвердить отдельно

1. **Почта и восстановление 2FA.** В окружении именно запущенной службы
   подтвердите обязательный второй фактор, получение обычного кода, отсутствие
   входа по одному паролю при недоступной отправке и процедуру восстановления.
   Резервные коды храните вне сервера. Репетируйте отказ доставки в изолированном
   окружении; не выключайте рабочую почту ради этой команды. Не помещайте код
   или скриншот с секретом в отчёт. `accepted` SMTP не доказывает попадание во
   входящие.
2. **Копия вне сервера.** Получите копию из реального удалённого хранилища и
   расшифруйте локально по [инструкции резервирования](../deploy/RELIABILITY.md).
   Не подменяйте это проверкой исходного локального архива. На отдельной чистой
   машине разверните закреплённый релиз и выполните
   `python3 deploy/recovery_check.py retrieved.tar.gz --source /path/to/matching/release`.
   Доступны должны быть сохранённые работы, файлы занятия и изображения.
   Зафиксируйте время всего пути, включая загрузку/расшифровку, и допустимую
   потерю данных. Время старта маленькой тестовой БД не равно времени восстановления VPS.
3. **Расписание и оповещения.** Проверьте фактически прошедшие плановые копии,
   выгрузки и получение уведомления о контролируемом отказе на стенде. Наличие
   cron/systemd-файла в репозитории не подтверждает выполнение расписания.
4. **Исполнитель.** Выполните все обязательные контейнерные тесты из
   [инструкции исполнителя](../deploy/python-runner/README.md) и сохраните JSON.
   Прогон GitHub не заменяет приёмку ядра, cgroup, systemd и Podman рабочего VPS.
5. **Миграция и реальные данные.** Запустите описанную проверку на обезличенной
   копии действительно использовавшейся старой версии. Затем в восстановленном
   стенде проверьте сохранённые результаты, доступ учителя и материалы.
   Синтетические записи из тестов не называйте старой рабочей БД.

Исходный JSON сохраняется как машинное свидетельство. Ручные результаты и
ограничения фиксируются отдельно в закрытом журнале развёртывания со временем,
релизом и окружением; не редактируйте исходный JSON, чтобы получить зелёный
статус. Сам скрипт не устанавливает службы и не выполняет развёртывание.
