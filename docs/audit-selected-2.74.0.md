# Проверки сервера, миграции и учебных материалов — 2.74.0

Область работы: пункты 2, 3 и 5 следующего этапа аудита. База кода —
`27ab70f` после объединения PR №236. Этот этап не выполняет развёртывание
на рабочем сервере и не меняет рабочую БД.

## 2. Рабочий сервер

17.11.2026 по московскому времени выполнены публичные запросы без cookies
к `https://egeshka.online/welcome` и `/api/health`. TLS проверен штатным
клиентом; оба запроса вернули 200 без перенаправления. Присутствуют CSP,
HSTS `max-age=31536000` и `nosniff`.

`/api/health` сообщил **2.72.0** при уже объединённой версии **2.73.1**.
Это свидетельство публичного endpoint в момент измерения, не проверка файлов
или службы изнутри VPS. Результат сохранён в
[production-public-check-2026-11-17.json](production-public-check-2026-11-17.json).

Доставка почты, обязательный второй фактор, восстановление входа и установленный
исполнитель остаются **pending**: доступа к терминалу VPS и конфигурации службы
в этом сеансе нет. Наличие успешных контейнерных тестов в GitHub не подтверждает
настройку VPS. Обычный учебный Python остаётся в браузере.

Проверка получила `--expected-version`: здоровый старый сайт больше нельзя
принять за целевой релиз только потому, что локальные файлы тоже старые.
В отчёте выводятся ожидаемая и фактически сообщённая версии.

## 3. Миграция рабочей базы

Новая команда `deploy/rehearse_upgrade.py` создаёт согласованный SQLite-снимок
через `mode=ro`, `query_only` и backup API, в том числе при работающем WAL.
Копия остаётся на той же машине в закрытом временном каталоге. Новый код
дважды запускает только миграции копии; сеть и почта дочернего процесса отключены.

Сравниваются схема, целостность, количество и значения записей 27 защищённых
таблицы, связи результатов и владельцев. Изменения существующих значений при
первом старте требуют разбора (`pending`); повторные изменения при втором старте
или новые нарушенные связи дают `fail`. Отчёт не содержит записей учеников,
паролей, кода или отпечатков частных записей.

Временный процесс предназначен для проверенного кода релиза. Python audit hook
запрещает сетевые сокеты и запуск дочерних процессов, но не является песочницей
операционной системы для запуска недоверенной программы.

Проверены синтетические случаи потери оценки при прежнем количестве строк,
повторного изменения награды, смены владельца, работающего WAL и очистки
временной копии. **Настоящая рабочая база ещё не проверена.**

## Команды для VPS

Используйте отдельный каталог проверенного кандидата 2.74.0. Не заменяйте им
`/opt/trainer` для выполнения проверки. Команды запускаются пользователем,
который может читать конфигурацию и БД приложения; пробу исполнителя выполняйте
с теми же правами, что и служба сайта. Каталог отчётов должен быть закрытым,
а имена JSON — новыми. Ненулевой код `pending` не означает аварийную остановку сайта.

```sh
candidate=/path/to/reviewed-egeshka-2.74.0
reports=/path/to/private-new-reports
python3 "$candidate/deploy/acceptance.py" \
  --app /opt/trainer --url https://egeshka.online \
  --expected-version 2.74.0 --probe-runner \
  --output "$reports/server-acceptance.json"
python3 "$candidate/deploy/rehearse_upgrade.py" \
  --installed-app /opt/trainer --candidate "$candidate" \
  --private-local-copy --output "$reports/migration-rehearsal.json"
```

До установки кандидата отличие публичной версии ожидаемо: это не разрешение
на развёртывание. Реальная доставка почты и восстановление входа проверяются
отдельно по [процедуре эксплуатационной приёмки](operations-acceptance.md).
Для сравнения с уже объединённой 2.73.1 используйте `--expected-version 2.73.1`.
Рабочую БД не требуется пересылать; для последующего разбора достаточно
агрегированных отчётов, сохранённых приватно.
