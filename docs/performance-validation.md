# Проверка готовности на уроке

Бюджеты ниже — проверяемые инженерные ограничения релиза. Это не опубликованный
SLA и не утверждение о скорости реальных школьных устройств.

| Профиль Chromium CI | Готовая главная | Открытие первого задания | Сумма блокирующего времени |
| --- | ---: | ---: | ---: |
| 1366×768, CPU ×4, 4 Мбит/с, RTT 100 мс | 10 с | 1,5 с | 2,5 с |
| 390×844, CPU ×6, 1,6 Мбит/с, RTT 150 мс | 16 с | 2,5 с | 4,5 с |

Готовность главной — видимый и доступный элемент выбора задания после отрисовки;
второй замер требует настоящее условие с доступным полем ответа. Пустой экран,
событие `load` или появление индикатора загрузки не считаются готовностью.
Блокирующее время — сумма частей задач главного потока длиннее 50 мс.
Эти потолки учитывают медленное соединение и запас для разделяемого CI runner:
они должны ловить существенную задержку, а не маскировать её повтором теста.
Автоматический повтор для этого профиля не включён. Менять бюджеты вслед за
регрессией можно только после разбора отчёта и согласованного изменения цели.

`npm run test:performance` из `tests/browser` использует 15 000 синтетических
заданий, холодный кеш и отгружаемые ресурсы. JSON и снимок сохраняются в отчёте
Playwright, включая все измеренные значения. Начальный JS ограничен 650 000 байт,
`app.js` — 300 000 байт сжатой передачи. `app-exams.js` (МЦКО и Интеллектуальный
мегаполис) и полная история версий до действия пользователя не запрашиваются.

## Воспроизводимый прогон на физическом школьном компьютере

Полевых результатов в репозитории пока нет. Следующие команды **нужно выполнить
на самом проверяемом компьютере**, а не на удалённом сервере или в облачном CI.

1. Взять конкретный проверяемый commit, установить Python 3.11+, Node 22 и зависимости
   `npm ci --ignore-scripts` в `tests/browser`. Для поставляемого Chromium выполнить
   там `npx playwright install chromium`; для установленного Chrome использовать
   `--channel chrome`. На Linux может потребоваться установка системных библиотек
   из документации Playwright. Песочницу браузера не отключать.
2. Сохранить модель компьютера, CPU, объём RAM, ОС, версию браузера, режим питания,
   состояние подключения к питанию и обычный набор запущенных школьных приложений.
   Не запускать только на свободном компьютере, если на уроке рядом работают IDE
   и другие программы. Исключить реальные ученические данные из отчёта.
3. Из корня репозитория выполнить:

   ```sh
   node tools/measure_school_device.cjs --device "Модель; CPU; RAM; ОС; питание; приложения" --output /private/school-pc-2026-11-16.json
   ```

   Скрипт открывает видимый браузер, создаёт только временные локальные тестовые
   аккаунты/БД, выполняет **5 холодных + 5 тёплых** открытий, сохраняет все значения,
   медиану и максимум. CPU не замедляется: измеряется реальное устройство.
   Сеть специально ограничена 4 Мбит/с и 100 мс; это сравнимый тест устройства,
   **не замер качества школьного Интернета**. Существующий отчёт не перезаписывается.
4. Проверить JSON: все 10 запусков завершены, доступны условие и поле ответа,
   медиана и худший запуск укладываются в выбранный бюджет. Зафиксировать commit
   рядом с отчётом, не переносить значения между релизами. Отдельно сохранить
   замечания по визуальному состоянию и работе с клавиатурой.
5. На реальном школьном соединении отдельно проверить тестовый HTTPS-стенд с
   вымышленными аккаунтами: готовность перед уроком, первый файл, первый запуск
   Python, сохранение ответа и восстановление после обрыва. Снять время до
   готовности и восстановления внешним секундомером/записью экрана минимум 5 раз.
   Этот дополнительный лист нужен для сетевой и эксплуатационной приёмки; локальный
   скрипт не измеряет прокси, DNS, TLS, Wi-Fi, фильтрацию CDN и ёмкость сервера.

Решение о поддержке конкретного устройства принимается по сохранённым результатам
этого устройства и сетевого прогона. Успех CI сам по себе такой приёмкой не является.
