# Границы обработчиков и нагрузка класса

R02 исправляется по частям: общий допуск отделяется от HTTP-обработчиков,
а предметные проверки остаются рядом с операцией. Перенос функции в другой файл
сам по себе не означает, что её авторизация или транзакция стали безопаснее.

## Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| `api_access.py` | Явный реестр методов/путей и общие условия доступа; вход в API и особые HTTP-транспорты. |
| `student_auth_http.py` | Вход, учётная запись, подтверждение почты, восстановление и смена пароля, ученические сессии. Зависимости передаются явно. |
| `teacher_auth_http.py` | Учительская сессия, вход и проверка кода, условия допуска и ограничения истёкшего доступа. |
| `task_http.py` | Открытие задания, проверка ответа, подсказка и разбор; сохранение результата до HTTP-подтверждения. |
| `bank_http.py` | Выдача банка через действующие ограничения и правила доступа. |
| `storage.py`, `economy.py` | Порядок блокировок, транзакции SQLite, откат и отправка ответа после commit. |
| `runtime_http.py` | Ограничение обычных и длительных соединений раздельными пулами. |
| `server.py` | Сборка зависимостей, статические ресурсы, оставшиеся учебные и учительские операции. |

Обработчики не импортируют `server`: он передаёт им сервисы. Общая проверка не
заменяет проверку владельца работы, класса, ученика или документа. При добавлении
маршрута нужно указать метод, путь и класс доступа и сохранить предметную проверку
владения. Неизвестный маршрут не получает доступ автоматически по префиксу.
Публичный вход или восстановление пароля разрешает только обмен реквизитами:
сам пароль, код или одноразовая ссылка всё равно проверяются обработчиком.

Для учётных изменений, финансовых и других явно транзакционных операций проверка
доступа выполняется внутри транзакционной границы. Ошибочный ответ откатывает
изменения; успешный HTTP-ответ отправляется
после commit. Ожидание при неверном пароле и сетевые операции не должны удерживать
общую блокировку БД. Рассылка подтверждений пока не имеет постоянной очереди:
отказ процесса между сохранением и отправкой письма требует повторного запроса.

## Соединения и системные ограничения

По умолчанию допускается 128 обычных HTTP-соединений и 256 длительных потоков.
Это задаётся `EGE_HTTP_WORKERS` и `EGE_STREAM_WORKERS`. Длительное соединение
переводится в отдельный пул после проверки доступа. Переполнение возвращает 503
с `Retry-After`; освобождение слота не зависит от успешного ответа обработчика.
Очередь принятия соединений — 128, таймаут обычного сокета — 60 секунд,
WebSocket занятия — 75 секунд с клиентскими ping. Это ограничения ресурсов,
а не обещание обслужить столько активных вычислений одновременно.

`deploy/ege-trainer.service` задаёт отдельного пользователя, `UMask=0077`,
`NoNewPrivileges`, `PrivateTmp`, ограничения записи, `TasksMax=512`,
`LimitNOFILE=8192` и 30 секунд на остановку. При изменении пулов следует проверить
общий лимит потоков вместе с фоновыми задачами. Возможность отправить письмо
и наличие reverse proxy проверяются отдельно на рабочем сервере.

## Воспроизводимый сценарий класса

```sh
python3 tools/load_lesson.py --students 30 --output /tmp/classroom-30.json
python3 tools/load_lesson.py --students 60 --output /tmp/classroom-60.json
python3 tools/load_lesson.py --students 60 --seconds 300 --interval 10 --output /tmp/classroom-soak.json
```

Скрипт всегда использует временную SQLite и синтетические аккаунты; URL и рабочую
БД передать нельзя. Ученик получает профиль и банк, открывает настоящее тестовое
задание, сохраняет код, отвечает и читает историю. Для продолжительного сценария
добавляются чтение и автосохранение. Сетевой путь — локальный loopback без TLS,
внешнего прокси и задержек Интернета. Искусственное время чтения задания сокращено;
серверная проверка ответа сохраняется.

Отчёт содержит p50/p95/максимум HTTP, p95/максимум ожидания блокировки БД,
ошибки, потребление памяти, параметры среды и SHA-256 исходников. Отдельное
соединение SQLite проверяет, что у каждого ученика ровно одна подтверждённая
попытка и одно сохранённое решение. Нулевое число ошибок при неверном числе
сохранений не считается успешным результатом.

Оба коротких сценария запускаются в GitHub CI; JSON сохраняются в артефакте
`classroom-load` соответствующего commit. Эти результаты характеризуют конкретный
стенд и сценарий. Предельная нагрузка рабочего VPS, реальные школьные устройства
и миграция настоящей обезличенной старой БД требуют отдельной приёмки.

## Оставшаяся работа

В `server.py` ещё остаются существенные учительские и учебные операции. Их следует
выносить последовательно, сохраняя регрессии прав доступа, транзакций и совместного
занятия. Переход на другой HTTP-фреймворк или СУБД не является условием этого этапа.
Наличие нового реестра не отменяет ревью изменений самой транспортной границы.
